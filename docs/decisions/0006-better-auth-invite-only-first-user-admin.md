# 0006. Better Auth with the organization plugin; invite-only sign-up, first user is admin

## Status

Accepted

## Context

bhidubot is a self-hosted team tool. Every account can spend transcription and LLM credits, so strangers must not
be able to sign up (spec §4.1). We need sessions, email+password and Google sign-in, teams with roles, and
email invitations, with the data in our own Postgres.

## Decision

`packages/auth` builds a Better Auth instance (`createAuth(deps)`) on the drizzle adapter, mounted at `/api/auth`,
with the organization plugin as our "teams" (organization = team, `member.role` = `TeamRole`).

Sign-up is invite-only, enforced in `databaseHooks.user.create.before`, which runs for every user-creation path
(email+password and social). `evaluateSignup` allows, in order:

1. the very first user, who becomes instance admin (`user.is_instance_admin`);
2. an email whose domain is in `ALLOWED_SIGNUP_DOMAINS`;
3. an email with a `pending`, unexpired invitation (matched case-insensitively);

and rejects everything else with `403 NOT_INVITED`.

The first-user rule is made race-safe by the database, not by application locks: a partial unique index
`one_instance_admin ON "user" (is_instance_admin) WHERE is_instance_admin` lets only one admin row commit.

The auth tables in `packages/db/src/schema/auth.ts` are generated by the Better Auth CLI
(`bun run auth:generate` in `packages/auth`, driven by the non-exported `src/auth.schema-config.ts`); the partial
index is hand-appended SQL in the migration.

## Why

A self-hosted team tool must not spend credits on strangers.

## Pros

- Sessions, organizations, roles and invitations come for free.
- Data lives in our own Postgres, next to the app's tables, under the same migrations.
- One hook covers all sign-up paths, so new providers cannot bypass the policy.

## Cons

- The generated schema is coupled to Better Auth upgrades; regenerate and diff on each upgrade.
- The first-user rule needs a database constraint to be race-safe; the losing concurrent sign-up gets an error
  rather than a friendly message.
- Better Auth's generated tables use `timestamp` without time zone (UTC wall-clock), unlike our own
  `timestamptz` tables; SQL comparing them against `now()` must use `now() at time zone 'utc'`.

## Alternatives considered

- Clerk: hosted, user data outside our database; it is what meeting-bot69 used.
- Lucia: deprecated.
- Hand-rolled auth: sessions, OAuth and invitations are security-sensitive work we'd rather not own.

## Consequences / follow-ups

- The API (Task 9) mounts `auth.handler` at `/api/auth/*` and resolves team access with `getMembership`, never from
  request bodies.
- Invitation emails link to `${APP_URL}/accept-invite/:id`; the web app must implement that route.
